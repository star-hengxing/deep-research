# deep-research 质量检测设计

## 核心矛盾

聊天记录中的关键对话：

> "怎么定义质量高？你会发现没法定义。"
> "没有我的思考，还是产出一堆垃圾。"
> "这是悖论，我要是知道答案，就不会去 research。"
> "你可以蒸馏一个你的验收标准，然后让 AI 按这个标准来。"

这不是 deep-research 独有的问题。Perplexity、Elicit、Stanford STORM 都面对同一个问题，它们的解法趋同：**不判断"好不好"，而是检测具体的缺陷信号。**

类比：代码 linter 不能告诉你代码是否优雅，但能检测未使用的变量、潜在空指针、圈复杂度过高。研究报告的"linter"也不需要判断"这篇报告好不好"，只需要检测**可度量的质量缺陷**。

## 设计原则

1. **不做整体评分**。"这篇报告 7.5 分"没有意义——用户也给不出基准分。
2. **检测缺陷，不评价优秀**。每个检查项要么 pass 要么 fail，附带具体位置和修复建议。
3. **分层检测**。格式层（已有）→ 结构层 → 证据层 → 内容层，逐层递进。
4. **人的判断力不可替代**。最终验收始终是人。质量门的价值是**在人审之前过滤掉明显的低质量**，减少人的审查负担。

## 四层质量门

### Layer 0: 格式层（现有 validate 命令）

已实现，检查：
- `.meta.json` 完整性
- URL 可访问性
- `---` 水平线警告
- 文件结构完整

### Layer 1: 结构层 — "报告骨架是否完整"

| 检查项 | 方法 | 判定 |
|--------|------|------|
| 章节覆盖 | 检查 README.md 的 H1/H2 标题是否覆盖 plan.md 中定义的所有方向 | 缺失方向 → fail |
| 摘要存在性 | 检查是否有"摘要"/"Executive Summary"段落，且 ≥100 字 | 缺失或过短 → fail |
| 参考文献存在性 | 检查是否有"参考"/"Bibliography"段落 | 缺失 → fail |
| 字数下限 | 总字数 ≥ 方向数 × 800 | 低于阈值 → warn |
| 方向报告完整 | 每个 agent 目录至少有一个 .md 报告文件 | 缺失 → fail |

**实现**：纯文本解析，不需要 LLM。

### Layer 2: 证据层 — "断言有没有根据"

这是业界共识的核心层。Perplexity（DRACO）、Elicit、Google（FACTS Grounding）、Stanford（STORM / FActScore）都以这一层作为质量的主要信号。

| 检查项 | 方法 | 判定 |
|--------|------|------|
| 引用密度 | 统计正文中 `[N]` 引用标记数量，除以段落数 | < 0.3 引用/段落 → warn |
| 孤立断言 | 找出包含数据/日期/百分比/排名但无 `[N]` 标记的句子 | 列出所有孤立断言供人审 |
| 引用可追溯 | 每个 `[N]` 标记在参考文献段中有对应条目 | 缺失条目 → fail |
| 幽灵引用 | 参考文献中存在但正文从未引用的条目 | 列出幽灵引用 → warn |
| 来源多样性 | 统计独立域名数量 | < 5 个独立域名 → warn |
| 来源三角验证 | 关键断言（含具体数据的句子）被 ≥2 个独立来源支持 | 列出单源关键断言供人审 |

**实现**：正则匹配 + 简单 NLP（句子分割、数字检测）。不需要 LLM 做验证，只需要找出"可疑"位置让人审。

### Layer 3: 内容层 — 不实现

内容层（AI 废话检测、套话匹配等）经实测效果有限——模式匹配的误报率高，且真正的内容质量判断无法脱离语境。这一层交给 agent prompt 约束和人工审查更合适。

## 不做什么

以下这些看起来诱人但实际上**不可行或不值得做**：

| 想法 | 为什么不做 |
|------|----------|
| LLM 评分报告整体质量 | LLM 倾向给高分、偏好冗长文本，且无法比人更懂你要什么 |
| 自动判断"分析是否深刻" | 这是用户的核心判断力，无法外包给机器 |
| 用 LLM 验证事实正确性 | LLM 自己就是幻觉来源，用它检查事实是循环论证 |
| 自动对比竞品报告质量 | 没有标准数据集，无法标定 |
| 用 LLM 改写低质量段落 | 这会掩盖问题而非解决，且破坏可追溯性 |
| 关键词匹配 AI 套话 | 误报率高，脱离语境的模式匹配不可靠 |

## 实施路线

### Phase 1: 把 Layer 1 + Layer 2 的正则检查集成到 `validate` 命令

不依赖 LLM，纯文本分析。输出格式：

```
╔══ Quality Gate ══╗
✓ Structure: 8/8 directions covered
✓ Summary: 352 words
✓ Bibliography: 19 entries

⚠ Evidence:
  - Citation density: 0.42/paragraph (OK)
  - 3 orphan claims with data but no citation:
    L47: "销量突破100万份" — no [N] tag
    L102: "市场份额达到23%" — no [N] tag
    L198: "2024年收入增长40%" — no [N] tag
  - 2 ghost references: [8], [15] (cited in bibliography, never used in body)
╚══════════════════╝
```

### Phase 2: 可选的 agent 子报告交叉检查

检查多个 agent 子报告之间的一致性：
- 同一事实在不同方向报告中的数据是否一致
- 综合报告（README.md）中的断言是否能在子报告中找到出处

### Phase 3: 信源质量分级（长期）

对 searched_links 的域名做分级：
- Tier 1: 学术（arxiv, scholar, doi.org）、官方文档
- Tier 2: 行业媒体、维基百科
- Tier 3: 博客、论坛、社交媒体
- 报告信源的 tier 分布作为参考指标

## 回应聊天中的核心问题

**"怎么定义质量高？"** — 不定义。定义"什么是明确的低质量"，然后检测它。

**"没有我的思考还是垃圾"** — 质量门不替代你的思考。它只是在你审之前，把"有数据没引用"、"同一数字前后矛盾"、"AI 套话太多"这类机械性问题先标出来。你的审查精力应该花在判断"分析是否有洞察"上，而不是数引用标记。

**"蒸馏你的验收标准"** — 这正是质量门词表的来源。每次你在审阅时发现一个让你不满的模式，就把它加到检测规则里。规则会随使用逐渐积累你的隐性标准。

## 参考

- Perplexity DRACO Benchmark: 40+ 条 rubric 评分，按维度二值判定
- Elicit Reports Eval: claim-level 分解 + 引用支持度评估
- Google FACTS Grounding: 二阶段（相关性 → 事实扎根）
- Stanford STORM / FActScore: 原子断言分解 + 信源验证
- LLM-as-Judge 综述 (arXiv 2411.15594): 分解判断优于整体评分
